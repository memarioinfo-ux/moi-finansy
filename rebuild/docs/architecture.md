# Архитектура «Мои финансы» v2

## Цели
Android-приложение для личного финансового учёта: счета, доходы, расходы, переводы, категории, история «Все», аналитика, распознавание банковских push и ручной разбор неизвестных сообщений. Офлайн — основной сценарий. Данные финансов не отправляются на сервер.

## Технологический план
- Android-хост: Kotlin, `NotificationListenerService` для уведомлений, Storage Access Framework для экспорта/импорта.
- Хранение на Android: SQLite/Room и транзакции БД; **не** `localStorage` как основной источник истины.
- Интерфейс: модульный Web UI внутри Android WebView (чтобы сохранить удобство прежнего интерфейса), без единого многотысячестрочного HTML-файла. Вариант UI пересматривается отдельно после проверки требований.
- Доменная модель: счета, операции в целых минимальных единицах валюты, неизменяемый входящий журнал уведомлений, связи `sourceNotificationId`, категории и правила определения магазина.
- Никакой прямой интеграции с банковскими API или считывания закрытых баз банка без отдельной авторизации/поддерживаемого интерфейса.

## Поток уведомлений
1. Android получает событие `onNotificationPosted` только после предоставления системного разрешения.
2. Событие **сразу фиксируется в постоянной базе** как raw event, с исходным текстом, пакетом приложения, временем и ключом дедупликации. Ничего не удаляется при ошибке разбора.
3. Отдельный обработчик делает попытку распознавания; статус: `pending`, `processed`, `needs_review` или `ignored`.
4. При успешном сопоставлении формируется операция с ссылкой на исходное уведомление; в одной транзакции БД записываются операция и статус события.
5. Повторное уведомление/повторный запуск парсера не создаёт дубль.
6. Вручную исправленные операции и исходные уведомления сохраняются для аудита. Автоочистки последних N событий не должно быть.

**Граница гарантии:** Android не может вернуть уведомления, не доставленные listener-у до выдачи доступа, после отзыва доступа или при ограничении ОС. Приложение должно явно показывать статус доступа и число необработанных событий.

## Финансовые инварианты
- Денежные суммы хранить целыми сотыми, не использовать двоичные float для расчётов.
- Доход увеличивает остаток счёта, расход уменьшает. Внутренний перевод списывает с одного и добавляет на другой, не считается доходом/расходом.
- Внутренний перевод в MVP — только между счетами с одинаковой валютой; обмен валют оформляется отдельно.
- «Все» — представление **единого журнала** операций с корректной сортировкой и фильтрацией, не второй независимый список данных.
- Удаление/изменение финансовых данных требует подтверждения; служебные и исходные записи не теряются без явного решения.

## Сохранение и перенос
- Резервная копия `schemaVersion` + счета + операции + категории + сырой журнал + метаданные + контроль целостности; экспорт и импорт с предварительной проверкой.
- После каждого обновления — миграция структуры БД, тесты upgrade path и проверка неизменности количества операций и итоговых балансов.
- Не допускать перезаписи старого состояния непроверенным импортом.
- Из старого приложения известен JS-ключ `alina_budget_state_v10`, но фактические данные находятся на Samsung внутри его приложения. До доступного экспорта/проверенной подписи **перенос не обещать**.
- Для обновления установленного APK без потери данных необходимо совпадение `applicationId` и сертификата подписи. Эти параметры v1.0.6.4 пока не подтверждены.

## Приёмочные этапы
0. **Аудит и защита данных.** Зафиксировать ветки, схему старого хранилища, получить безопасную резервную копию/подход к её получению; не менять приложение на Samsung.
1. **Финансовое ядро.** Проверенные счета/операции/переводы/категории, единый список «Все», автотесты денежных инвариантов.
2. **Android + БД + интерфейс.** APK с экраном счетов, добавлением/редактированием операции, историей и аналитикой.
3. **Банковские уведомления.** Журнал raw push, парсеры Mbank/Беларусбанк/Альфа-Банк и др. только на тестовых примерах, защита от дублей и разбор нераспознанных.
4. **Бэкапы и совместимость.** Экспорт/импорт, проверка миграции, ключа подписи, установка обновлений поверх существующей тестовой версии.
5. **Релиз.** Сквозные проверки, README сборки и воспроизводимая подпись; только после подтверждённого переноса старой истории.

## Что пока не установлено
Точный `applicationId` и сертификат установленной v1.0.6.4, наличие исходного keystore, конкретные примеры всех банковских push, полная схема старых native-очередей. Сборку без этих проверок нельзя считать безопасным обновлением.
